# ФСП Карьера — платформа обратного найма

Кандидат один раз проходит адаптивный тест-квест и попадает в категорию «специализация · трек · грейд». Работодатель описывает потребность текстом, получает анонимную подборку с объяснением оценки и шлёт приглашение-оффер с обязательной вилкой. Контакты раскрываются только после принятия.

```
frontend/   кликабельный интерфейс (один index.html, брендбук ФСП), ходит в API
backend/    FastAPI + Postgres: API, подбор, тест на IRT, интеграции, лотерея, синтетика, валидация
```

## Запуск

```
export SANDBOX_TOKEN=$(openssl rand -hex 32)                # общий секрет API ↔ песочница; без него тест идёт без задач на код
DEMO=1 docker compose up -d --build                         # стенд для жюри; без DEMO=1 — боевой режим
docker compose exec api python -m seed.generate --reset      # демо-персонажи + 1500 кандидатов, 250 потребностей
docker compose exec api python -m app.services.validation    # метрики для дашборда /v
```

Открыть http://localhost:8000. Документация API: http://localhost:8000/docs. Вкладки «Кандидат» и «Работодатель» в шапке входят за демо-персонажей (Дмитрий Орлов, A-1042, и «Ладога Пэй»).

Локальная LLM необязательна. Если запущен `ollama serve` с моделями из `LLM_MODEL` / `EMBED_MODEL` (по умолчанию `qwen2.5:32b-instruct` и `bge-m3`), разбор потребностей и резюме и реранк топ-30 идут через неё. Если нет, всё работает на правилах и справочнике навыков.

Без Docker для API: `docker compose up -d db`, затем `cd backend && uv run python -m seed.generate --reset && DEMO=1 uv run uvicorn app.main:app --port 8000`.

`DEMO=1` открывает вход за демо-персонажей, отдаёт код подтверждения почты прямо в ответе и пускает по ФСП ID без OAuth. Это нужно только для стенда жюри; по умолчанию режим выключен. Без него коды приходят письмом — задайте `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`; без SMTP вход по почте вернёт 503. Новый код можно запросить не чаще раза в минуту. Коды хранятся как HMAC с серверным ключом — задайте постоянный `SECRET_KEY`, иначе коды сгорают при перезапуске.

Схема БД ведётся миграциями Alembic (`backend/migrations/`). API при старте сам накатывает все ревизии (`alembic upgrade heads`) под advisory-блокировкой; база, созданная до Alembic (`create_all`), сначала помечается ревизией `0001_baseline`, данные сохраняются. Вручную, тем же путём, что при старте: `cd backend && uv run python -c "from app.db import init_db; init_db()"`. Голый `uv run alembic upgrade heads` годится для пустой базы или уже под Alembic (база от `create_all` его не пройдёт — её помечает только `init_db`); текущая ревизия — `uv run alembic current`. Если модель изменили без ревизии или в базе ревизия от другой ветки, API не стартует и пишет, что делать. `seed.generate --reset` пересоздаёт схему целиком (`DROP SCHEMA public CASCADE` + миграции). `docker compose down -v` — крайняя мера, стирает все данные.

Тесты: каждый набор работает в своей базе, `./backend/test.sh` создаёт базы, прогоняет все и проверяет покрытие (порог 80 %, сейчас 95 %). Фронт: `cd frontend && npm ci && npx playwright install chromium && npm test` — Playwright сам поднимает бэкенд на своей базе `fsp_e2e` и проходит сценарии кандидата и работодателя; порог покрытия JS — 80 %, сейчас 87,0 % строк (с песочницей; без неё сценарий задачи на код пропускается). Песочница проверяется своими тестами против настоящего nsjail — раздел «Песочница». Живые запросы к Codeforces и CTFtime включаются через `LIVE=1`. CI — `.github/workflows/ci.yml`. Правила работы в репозитории — `CLAUDE.md`, статус задач — `table.md`.

## Как устроено

| Часть | Где | Суть |
|---|---|---|
| Тест-квест | `services/irt.py`, `services/items.py`, `routers/quest.py` | 2PL IRT, EAP-оценка θ ± SE, выбор задания по максимуму информации. Банк — параметрические шаблоны: клоны семейства отличаются данными, разброс сложности ~0,05, утечка одного клона не раскрывает остальные. Грейд повышается, только если θ − SE выше порога (гистерезис), не чаще раза в 90 дней; понижение сразу. Флаги несогласованности и слишком быстрых ответов. |
| Задачи на код | `services/code_items.py`, `services/sandbox.py`, `sandbox/`, `POST /api/quest/answer`, `POST /api/quest/run` | Одна задача на код за тест (после четырёх заданий): простые алгоритмы — суммы на отрезках, частоты через словарь, скобки на стеке, бинарный поиск, два указателя, поиск в сдвинутом массиве (пилотное). Решение на Python или TypeScript исполняется в своей песочнице (nsjail) на скрытых тестах, засчитано — все тесты пройдены. Подробности и ограничения — раздел «Песочница». |
| Подбор | `services/matching.py`, `routers/employer.py` | Фильтр категории → поиск по навыкам или эмбеддингам → `match` (θ с поправкой на SE, покрытие обязательных и желательных навыков, достижения) → итог `match × (0,5 + 0,5·P(принятия)) × штраф за нагрузку`. В ранжировании нет ФИО, пола, возраста и вуза. |
| Регуляторы | `catalog.py` | Вилка обязательна: нижняя граница не ниже 25-го перцентиля рынка, ширина ≤ 40 %. Квота работодателя 10 в неделю, 12 при доле принятых от 50 %. Ёмкость кандидата — 4 открытых приглашения. Срок ответа 7 дней, отказ с причиной. |
| Достижения | `integrations/`, `routers/achievements.py` | Codeforces: владение подтверждается кодом в поле «Организация», дальше рейтинг и места в раундах. CTFtime: рейтинг команды и места; подтверждает организатор. Хакатоны и ФСП: импорт протокола организатора в CSV или JSON (`POST /api/achievements/import`). Всё сводится в сигнал ∈ [0, 1]: влияет на место внутри категории, на грейд не влияет, без достижений — без штрафа. |
| Лотерея | `services/lottery.py`, `routers/lottery.py` | Квалифицированная лотерея (Frey & Osterloh): работодатель задаёт порог, пул прошедших замораживается и публикуется `sha256(seed)`, затем жребий. Любой может проверить результат по `pool_ids` и раскрытому `seed`. В пул не попадают те, кто за последние 90 дней отказал этой компании. |
| Синтетика | `seed/generate.py`, `seed/gold.py` | Сначала структура, потом текст: истинный θ, навыки, завышенные резюме (10 %), достижения у ~30 %, CF у ~13 %. Сложные контрпримеры: соседняя специализация, вилка ниже ожиданий. Эталонная релевантность 0–3 считается правилами по скрытым полям, без LLM. |
| Валидация | `services/validation.py`, экран `/v` | Precision@10 и nDCG@10 трёх версий подбора, симуляция рынка, LLM-читер, стабильность. |
| Резюме и PDF-профиль | `services/parsing.py`, `services/profile_pdf.py`, `GET /api/candidate/profile.pdf` | Из PDF-резюме — навыки, стаж и категория (для подбора), а также контакты, роли, софт-скиллы и места работы. Контакты только предзаполняют форму самого кандидата; роли и софт-скиллы — справочные (по справочникам `catalog.ROLES` и `SOFT_SKILLS`), видны в карточке, но не влияют на ранжирование и грейд. PDF-профиль — документ кандидата для себя: категория, компетенции θ ± SE, навыки, опыт, достижения, ожидания; места работы в нём — распознанные из резюме, кандидат видит их в профиле с пометкой и может исключить. Шрифт — JetBrains Mono, недостающие глифы (арабица, грузинский, часть эмодзи) — DejaVu Sans, остальное (CJK, большинство эмодзи) — «□». |
| Поиск по банку | `GET /api/employer/search` | Вся база без привязки к потребности: фильтры по специализации, треку, грейду, стеку, ФСП, CF, хакатонам; фасеты; ранжирование по силе подтверждённого профиля. |
| План теста по вакансии | `POST /api/quest/plan`, публичный `/plan/preview` | Из описания вакансии — веса компетенций (навык → компетенция), диапазон сложности вокруг порога грейда, примеры заданий. Тест по приглашению смещает выбор заданий к этим компетенциям; на грейд это не влияет. |
| Вакансии и отклики | `routers/vacancies.py` | Дополнительный сценарий: вилка обязательна, мягкий лимит 10 откликов в неделю, контакты видны работодателю сразу — кандидат откликнулся сам (запись в журнал). |
| Задания от работодателей | `routers/tasks.py` | Витрина без уведомлений и задача в приглашении. Оценка решения — свежий сигнал в карточке кандидата, на грейд и место в выдаче не влияет. |
| Внутренний чат | `routers/chat.py`, `services/chat.py`, экраны `/c/chat`, `/e/chat` | Дополнительный сценарий (в ТЗ не требуется): переписка кандидата с компанией без обмена контактами вне платформы. Писать можно, пока приглашение принято или отклик не отозван и не отклонён; кандидат свою историю читает всегда. Работодатель читает диалог, только пока ему открыты контакты — принятое приглашение или отклик, который кандидат не отозвал (после отказа компании история остаётся); отзыв отклика или согласия на обработку закрывает диалог для работодателя. Кнопка «Написать» появляется, только когда чат откроется; кандидат не пишет компании, от которой скрыл профиль. 2000 символов, 20 сообщений в минуту, мгновенная доставка через SSE (`GET /api/chat/stream`, подписчики в памяти одного процесса), непрочитанные и отметка «прочитано»; доступ закрывается и при внесении компании в «скрыть профиль от». Переписка входит в выгрузку данных и удаляется вместе с аккаунтом. API: `GET /api/chat/stream`, `GET /api/chat/contacts`, `GET /api/chat/unread`, `GET/POST /api/chat/{peer}`, `POST /api/chat/{peer}/read` (peer — id компании у кандидата и публичный id кандидата у работодателя; `before_id`/`after_id` для истории). |
| Неподтверждённые компании | `catalog.UNVERIFIED_QUOTA` | Работают сразу (верификация в MVP не обязательна), но с квотой 3 в неделю; кандидат видит плашку «компания не подтверждена». Автоматические проверки — контрольная сумма ИНН и почта входа (подтверждённая кодом) на домене сайта компании; кандидат видит «почта на домене подтверждена», а не «компания подтверждена»: связь ИНН с юрлицом проверяется только через реестр (следующий шаг). |
| 152-ФЗ | `routers/candidate.py`, `AuditLog` | Раздельные согласия (обработка, публикация карточки, внешние данные) с датой и версией; без согласия на публикацию кандидат не виден. Выгрузка своих данных, удаление аккаунта, журнал раскрытий контактов. Согласие действует только для текущей версии текста. Токены — sha256, коды входа — HMAC с серверным ключом, код Codeforces — хеш со сроком. |

## Песочница (задачи на код)

**Как устроено.** В тесте одна задача на код — после четырёх рабочих заданий (`irt.CODE_AT`), если песочница настроена и отвечает на `/health` (проверка раз в 30 с). Пилотная задача на код может прийти раньше, на месте пилотного задания; тогда рабочей задачи на код в этой сессии нет. Семейства (`services/code_items.py`), a и b — экспертная оценка до калибровки, как у остальных семейств:

| Семейство | Что проверяет | Чем отличаются клоны | a | b |
|---|---|---|---|---|
| `code_hash_count` | подсчёт частот словарём | самое частое (при равенстве — меньшее) / первый уникальный / сколько значений встречается ≥ k раз | 1,5 | −1,4 |
| `code_prefix_sums` | префиксные суммы | отрезок [l, r] с 0 / полуинтервал [l, r) / [l, r] с 1 | 1,6 | −1,0 |
| `code_brackets` | стек | правильность / глубина вложенности; набор скобок; пропуск прочих символов | 1,6 | −0,6 |
| `code_binary_search` | бинарный поиск по запросам | < x / ≤ x / первый ≥ x / в отрезке [lo, hi] | 1,7 | 0,0 |
| `code_two_pointers` | два указателя | пары с суммой ≤ t / < t / ≥ t | 1,7 | 0,6 |
| `code_rotated_search` (пилотное) | поиск в циклически сдвинутом массиве | индекс или −1 / есть ли | 1,5 | 1,2 |

У клона своё имя функции, своя деталь условия и свои данные; кандидат видит условие, сигнатуры на Python и TypeScript и 1–2 открытых примера. Скрытые тесты (10–15: примеры, крайние случаи, случайные и большой на 10⁵ — O(n·q) не укладывается в лимит) пересоздаются из сида клона при проверке, ожидаемые ответы считает эталон на Python. Эталоны на обоих языках проходят все скрытые тесты в настоящей песочнице (`sandbox/tests/test_references.py`), шаблон из условия — нет. В базе — только условие, примеры и сид; наружу не уходят ни сид, ни скрытые тесты, ни эталон.

- Ответ: `POST /api/quest/answer {item_id, lang: "python" | "typescript", code, ms, pasted}` → то же состояние сессии, что у других заданий, без вердикта: правильность, как и везде, не показываем до конца теста. Засчитано, если пройдены все скрытые тесты (бинарный исход 2PL). В сессию пишутся язык, код и сводка по тестам — статусы и время, без входных данных.
- «Запустить на примерах»: `POST /api/quest/run {item_id, lang, code}` → `{status, passed, total, results: [{status, time_ms, got, expected}], stderr, runs_left}` — только открытые примеры, до 20 запусков на задачу, на оценку не влияет. Статусы: ok, wrong, tle, mle, re, ce.
- Песочница недоступна или перегружена — 503 с понятным текстом, задание помечается `void`: не засчитывается ни в плюс, ни в минус, сессия продолжается со следующего задания.
- Флаги: `code_pasted` — верное решение больше чем наполовину вставлено из буфера (счётчик вставок на клиенте; обходится, поэтому только сигнал для разбора), `too_fast` — как у остальных заданий (лимит на задачу 15 минут). Оба дают `review_required` и не влияют на грейд.
- TypeScript исполняется Node 22 с `--experimental-strip-types`: типы стираются без проверки, `enum` и `namespace` не поддерживаются (сказано в задании; ошибка — «ошибка компиляции» с текстом Node).

**Модель безопасности** (`sandbox/`, Python stdlib + nsjail 3.4):

- Отдельный контейнер `sandbox` во внутренней сети compose (`internal: true`): портов на хост нет, выхода наружу нет, с ним говорит только `api` по общему секрету `SANDBOX_TOKEN` (заголовок `X-Sandbox-Token`, сравнение за постоянное время). Код кандидата и тесты не покидают нашу инфраструктуру — поэтому не e2b и не другие внешние песочницы (152-ФЗ).
- Каждый тест — отдельный запуск nsjail: свои пространства имён (пустая сеть, pid, mount, user, uts, ipc, cgroup), uid/gid 65534 без capabilities и с `no_new_privs`, очищенное окружение. Корень собран из нужного на чтение (`/usr`, `/lib`, `/bin`, `/dev/null`, `/dev/urandom`, `/dev/zero`), решение — `/task` на чтение, запись — только в tmpfs `/tmp` на 8 МБ. Корень самого контейнера — тоже только на чтение.
- Лимиты на тест: 2 с по стенке (меряется снаружи, превышение — tle), RLIMIT_CPU, 256 МБ в cgroup v2 без свопа (куча V8 — 192 МБ), 32 процесса и потока, 1 CPU, файлы и stdout до 8 МБ, 64 дескриптора. На запрос: код до 20 КБ, до 50 тестов, тело до 8 МБ, все тесты — до 60 с. Одновременно 4 прогона (`SANDBOX_WORKERS`), в очереди до 32 запросов, место ждём до 20 с, дальше 503.
- seccomp (`sandbox/policy.kafel`): процесс убивается на ptrace, mount и новом API монтирования, unshare/setns, bpf, perf_event_open, userfaultfd, keyctl, модулях ядра, kexec, clone с флагами новых пространств имён; `socket` — EPERM; `clone3` и io_uring — ENOSYS (glibc и libuv откатываются на обычные вызовы).
- Ожидаемые ответы внутрь nsjail не попадают: решение получает только аргументы, сравнение — снаружи. Фрагмент ошибки (до 400 символов) кандидат видит только для открытых примеров; при отправке API его не отдаёт и не хранит.
- Проверено тестами против настоящего nsjail (CI job `sandbox`): сеть наружу и к соседним сервисам, fork-бомба, бесконечный цикл, 2 ГБ памяти, запись вне `/tmp`, чтение `/etc/passwd` и файлов сервиса, секрет из окружения и `/proc/1/environ`, `os.system` и `child_process`, ptrace/unshare/mount через ctypes, поток вывода, подделка строки результата.
- **Ограничения.** nsjail работает в privileged-контейнере: без этого в Docker нет пространств имён и записи в cgroup. Ядро общее с хостом — уязвимость ядра даёт выход и из песочницы, и из контейнера на хост; seccomp и непривилегированный uid сужают поверхность, но виртуализацию не заменяют. При боевой нагрузке песочницу стоит вынести на отдельную ВМ (или gVisor/Firecracker), тогда privileged ограничен этой ВМ. Время меряется по стенке: на перегруженном хосте возможен ложный tle, поэтому лимит в 5–10 раз выше времени эталона, а прогоны ограничены числом CPU.
- **Ресурсы.** Контейнер `sandbox` — 4 CPU, 3 ГБ, 512 процессов (`cpus`, `mem_limit`, `pids_limit` в compose). На стенде 8 CPU / 32 ГБ API и Postgres остаётся 4 CPU. Проверка одного решения: Python — до ~1 с, TypeScript — ~2 с (старт Node ≈ 120 мс на тест), эталон на большом тесте — до 0,3 с.

Compose поднимает `sandbox` вместе с API; без `SANDBOX_TOKEN` песочница не стартует, а API не выдаёт задач на код. Тесты песочницы: `docker build --target test -t fsp-sandbox-test sandbox && docker run --rm --privileged -v "$PWD/backend/app/services/code_items.py:/srv/code_items.py:ro" fsp-sandbox-test`. E2E с песочницей: `docker build --target runtime -t fsp-sandbox sandbox && docker run -d --rm --name sbx --privileged -p 127.0.0.1:8091:8080 -e SANDBOX_TOKEN=dev fsp-sandbox`, затем `SANDBOX_URL=http://127.0.0.1:8091 SANDBOX_TOKEN=dev npm test`. Без `SANDBOX_URL` сценарий `09-code` локально пропускается. В CI песочница настоящая (job `frontend-e2e`), фейковой нет.
