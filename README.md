# ФСП Карьера — платформа обратного найма

Кандидат один раз проходит адаптивный тест-квест и попадает в категорию «специализация · трек · грейд». Работодатель описывает потребность текстом, получает анонимную подборку с объяснением оценки и шлёт приглашение-оффер с обязательной вилкой. Контакты раскрываются только после принятия.

```
frontend/   кликабельный интерфейс (один index.html, брендбук ФСП), ходит в API
backend/    FastAPI + Postgres: API, подбор, тест на IRT, интеграции, лотерея, синтетика, валидация
```

## Запуск

```
export SANDBOX_TOKEN=$(openssl rand -hex 32)                # общий секрет API ↔ песочница; без него тест идёт без задач на код
DEMO=1 docker compose up -d --build                         # стенд для жюри; без DEMO=1 — боевой режим
docker compose exec api python -m seed.generate --reset      # демо-персонажи + 1500 кандидатов, 250 потребностей
docker compose exec api python -m app.services.validation    # метрики для дашборда /v
```

Даты синтетики. Все сроки в засеве (приглашения, неделя квоты, даты тестов и достижений) отсчитываются от «сегодня» синтетики — по умолчанию 2026-10-05, дата макета; `--today YYYY-MM-DD` её меняет. Валидация считает открытые приглашения и нагрузку на ту же дату (у неё тот же `--today`), а не на реальный день, поэтому цифры ниже воспроизводятся в любой день. Смена даты сдвигает все сроки целиком, и цифры не меняются (проверено засевом от понедельника и от четверга). API живёт по реальным часам, поэтому интерфейс выглядит как в макете только какое-то время после даты демо. Два открытых приглашения у Орлова видны до четверга 2026-10-08, 12:00 МСК: приглашение «Кипрея» отправлено за 4 дня до даты демо и живёт 7 дней. Квота «Ладога Пэй» 6 из 10 держится до конца недели, потом приглашения истекают. Чтобы показать интерфейс в другой день, засейте от текущего момента: `seed.generate --reset --today now` (так засевает e2e). Валидацию запустите сразу после засева с `--today now`; через API — `POST /api/validation/run?today=now` с токеном организатора.

Открыть http://localhost:8000. Документация API: http://localhost:8000/docs. Вкладки «Кандидат» и «Работодатель» в шапке входят за демо-персонажей (Дмитрий Орлов, A-1042, и «Ладога Пэй»).

LLM необязательна: по умолчанию `LLM_PROVIDER=none` и всё работает на правилах и справочнике навыков — так стенд жюри обходится без GPU и ключей, а валидация (`app.services.validation`) всегда детерминирована на правилах. Модель, если включена, помогает в трёх местах: разбор текста потребности и резюме (ответ проверяется по справочникам, суммы всегда берутся из правил), реранк топ-30 подборки (только структурные поля без ФИО), эмбеддинги для поиска. Любой сбой, таймаут или мусор в ответе → правила, модель не дёргается минуту. Текст резюме и потребности уходит в модель только после маскировки ПДн (`parsing.mask_pii`: ФИО, почта, телефон, Telegram, ссылки на профили, адрес, дата рождения, гражданство → метки; это правила, а не NER — ограничения в `table.md`); контакты распознаются правилами локально.

Пример: `LLM_PROVIDER=ollama docker compose up -d --build` или `LLM_PROVIDER=gigachat GIGACHAT_AUTH_KEY=… LLM_CA_BUNDLE=/certs/russian_trusted_root_ca.pem docker compose up -d` (файл сертификата смонтируйте в контейнер). `EMBED_MODEL=none` выключает эмбеддинги, `LLM_TIMEOUT` — таймаут запроса, с. Векторы считаются при сохранении профиля и потребности; если у кого-то вектора нет или размерность другая (сменили модель), подбор идёт по навыкам. Ключи — только из окружения. Живой смоук: `cd backend && LIVE_LLM=1 LLM_PROVIDER=ollama uv run pytest -q -s tests/test_llm_live.py` (замеры — в `table.md`).

Без Docker для API: `docker compose up -d db`, затем `cd backend && uv run python -m seed.generate --reset && DEMO=1 uv run uvicorn app.main:app --port 8000`.

`DEMO=1` открывает вход за демо-персонажей, отдаёт код подтверждения почты прямо в ответе и включает мок-провайдер «ФСП ID (демо)». Это нужно только для стенда жюри; по умолчанию режим выключен. Без него коды приходят письмом — задайте `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`; без SMTP вход по почте вернёт 503. Новый код можно запросить не чаще раза в минуту. Коды хранятся как HMAC с серверным ключом — задайте постоянный `SECRET_KEY`, иначе коды сгорают при перезапуске.

Вход через ФСП ID — настоящий OpenID Connect (Authorization Code + PKCE S256): `POST /api/auth/fsp/start` → страница провайдера → `GET /api/auth/fsp/callback` (проверка state и куки браузера, обмен кода, подпись id_token по JWKS, iss/aud/exp/nonce, userinfo) → одноразовый билет во фрагменте адреса → `POST /api/auth/fsp/exchange` → наш токен; `POST /api/auth/fsp/unlink` — отвязать. Боевого Keycloak на хакатоне нет, поэтому в том же приложении живёт мок-провайдер `/mock-fsp-id` (discovery, authorize со списком демо-аккаунтов, token, userinfo с подтверждёнными участиями и местами, JWKS с RS256-ключом на процесс); он включён при `DEMO=1` или `FSP_ID_MOCK=1`. Переключиться на Keycloak — только конфигурацией: `FSP_ID_ISSUER=https://<host>/realms/<realm>` (только https), `FSP_ID_CLIENT_ID`, `FSP_ID_CLIENT_SECRET` (confidential-клиент), `PUBLIC_URL` (адрес стенда; из него — redirect URI `PUBLIC_URL/api/auth/fsp/callback`, переопределяется `FSP_ID_REDIRECT_URI`), `FSP_ID_SCOPE` (по умолчанию `openid email profile`). Достижения — claim `fsp_achievements` в userinfo (в Keycloak — protocol mapper только из атрибута, который правит реестр ФСП, а не пользователь: claim считается подтверждённым и обновляет общие события `source='fsp'`) в формате протокола импорта; пишутся, только если у кандидата действует согласие на внешние данные. Новый аккаунт создаётся только по почте, подтверждённой в ФСП ID, и только кандидатом; существующий аккаунт с той же почтой связывается сам, только пока в нём нет профиля или компании, иначе — «Связать с ФСП ID» в настройках после входа по коду. У боевого issuer redirect URI — только https (без `PUBLIC_URL` или `FSP_ID_REDIRECT_URI` на https кнопка ФСП ID выключена); рядом с боевым `FSP_ID_ISSUER` мок выключен.

Нагрузка и ресурсы. API работает одним процессом uvicorn (`WEB_CONCURRENCY=1` в `Dockerfile` и compose): уведомления чата по SSE, троттлинг запросов к Codeforces/CTFtime и ключ `SECRET_KEY` по умолчанию живут в памяти процесса, второй процесс сломал бы их. Нагрузочный прогон — `backend/loadtest/locustfile.py` (команда в докстринге): 50 одновременных пользователей обоих кабинетов на полном сиде — 0 ошибок, ~29 запросов в секунду, p95 подборки 170 мс, поиска по банку 190 мс; предел одного процесса — ~72 запроса в секунду. Стек `docker compose` под этой нагрузкой занимает ~1–1,5 ядра и до ~320 МБ памяти (api до 253 МиБ, db до 61 МиБ; в простое 119 и 34 МиБ), GPU не нужен. Песочница задач на код — отдельный контейнер с потолком 4 CPU / 3 ГБ (`cpus`, `mem_limit` в compose), занята только во время проверки решений. Подробные цифры — в `table.md`.

Схема БД ведётся миграциями Alembic (`backend/migrations/`). API при старте сам накатывает все ревизии (`alembic upgrade heads`) под advisory-блокировкой; база, созданная до Alembic (`create_all`), сначала помечается ревизией `0001_baseline`, данные сохраняются. Вручную, тем же путём, что при старте: `cd backend && uv run python -c "from app.db import init_db; init_db()"`. Голый `uv run alembic upgrade heads` годится для пустой базы или уже под Alembic (база от `create_all` его не пройдёт — её помечает только `init_db`); текущая ревизия — `uv run alembic current`. Если модель изменили без ревизии или в базе ревизия от другой ветки, API не стартует и пишет, что делать. `seed.generate --reset` пересоздаёт схему целиком (`DROP SCHEMA public CASCADE` + миграции). `docker compose down -v` — крайняя мера, стирает все данные.

Тесты: каждый набор работает в своей базе, `./backend/test.sh` создаёт базы, прогоняет все и проверяет покрытие (порог 80 %, сейчас 97 %). Фронт: `cd frontend && npm ci && npx playwright install chromium && npm test` — Playwright сам поднимает бэкенд на своей базе `fsp_e2e` и проходит сценарии кандидата и работодателя; порог покрытия JS — 80 %, сейчас 86,6 % строк (с песочницей; без неё сценарий задачи на код пропускается). Песочница проверяется своими тестами против настоящего nsjail — раздел «Песочница». Живые запросы к Codeforces и CTFtime включаются через `LIVE=1`. CI — `.github/workflows/ci.yml`. Правила работы в репозитории — `CLAUDE.md`, статус задач — `table.md`.

## Как устроено

| Часть | Где | Суть |
|---|---|---|
| Тест-квест | `services/irt.py`, `services/items.py`, `routers/quest.py` | 12 специализаций: восемь разработческих и четыре нетехнические ИТ-роли — Analysis (системный и бизнес-аналитик), Management (project и product), Design (UX/UI и продуктовый), SysAdmin / Support; у каждой свой банк сценарных заданий (`services/bank/`). 2PL IRT, EAP-оценка θ ± SE, выбор задания по максимуму информации. Банк — параметрические шаблоны: клоны семейства отличаются данными, разброс сложности ~0,05, утечка одного клона не раскрывает остальные. Грейд повышается, только если θ − SE выше порога (гистерезис), не чаще раза в 90 дней; понижение сразу. Флаги несогласованности и слишком быстрых ответов. Банки — 28–29 сценарных семейств на специализацию, включая сложные уровня Senior/Lead (`services/bank/`), плюс задачи на код у пяти специализаций с «Алгоритмами»; средняя SE полного теста 0,32–0,33 (валидация ниже). Экспресс-режим для знакомства (`mode: "express"`): 5 заданий по минуте без ревью и задач на код, SE ≈ 0,47, грейд выше Middle почти не присваивается, только предварительная категория с пометкой «экспресс-оценка» — ставится, если грейда ещё нет, кулдаун не запускает и существующий грейд не меняет. |
| Задачи на код | `services/code_items.py`, `services/sandbox.py`, `sandbox/`, `POST /api/quest/answer`, `POST /api/quest/run` | Одна задача на код за полный тест (после четырёх заданий; в экспресс-режиме её нет — за 60 с функцию не написать): простые алгоритмы — суммы на отрезках, частоты через словарь, скобки на стеке, бинарный поиск, два указателя, поиск в сдвинутом массиве (пилотное). Решение на Python или TypeScript исполняется в своей песочнице (nsjail) на скрытых тестах, засчитано — все тесты пройдены. Подробности и ограничения — раздел «Песочница». |
| Подбор | `services/matching.py`, `routers/employer.py` | Фильтр категории → поиск по навыкам или эмбеддингам → `match` (θ с поправкой на SE, покрытие обязательных и желательных навыков, достижения) → итог `match × (0,5 + 0,5·P(принятия)) × штраф за нагрузку`. В ранжировании нет ФИО, пола, возраста и вуза. |
| Кандидаты без теста | `matching.tested`, `category_grade`, `order_key` | Не скрываются: попадают в подборку и поиск по заявленному грейду с пометкой «грейд не подтверждён тестом», без θ, перцентиля и компетенций, и всегда стоят после прошедших тест (вклад θ — 0). Строгий порядок, а не штраф: грейд без теста — только слова кандидата (в синтетике 10 % резюме завышены), и любой конечный штраф позволил бы заявленному стеку обогнать подтверждённый. В лотерею не попадают: порог лотереи — квалификация, жребий уравнивает всех прошедших. Если тест показал грейд ниже заявленного, кандидат в категории по тесту, а в карточке видно «заявлен Senior, тест — Middle». |
| Регуляторы | `catalog.py` | Вилка обязательна: нижняя граница не ниже 25-го перцентиля рынка, ширина ≤ 40 %. Квота работодателя 10 в неделю, 12 при доле принятых от 50 %. Ёмкость кандидата — 4 открытых приглашения. Срок ответа 7 дней, отказ с причиной. |
| Достижения | `integrations/`, `routers/achievements.py` | Codeforces: владение подтверждается кодом в поле «Организация», дальше рейтинг и места в раундах. CTFtime: рейтинг команды и места; подтверждает организатор. Хакатоны и ФСП: импорт протокола организатора в CSV или JSON (`POST /api/achievements/import`): место, результат (победитель / призёр / финалист / участник отбора), дисциплина ФСП, спортивный разряд. Иерархии соревнований нет: вес — только результативность (0,8 / 0,6 / 0,35 / 0,05), число соревнований — с убывающей отдачей (k-е по силе ×0,5ᵏ), поэтому онлайн-явки профиль не набивают; рейтинг Codeforces — отдельное слагаемое. Разряд и дисциплина — факты в карточке, на вес не влияют. Всё сводится в сигнал ∈ [0, 1]: влияет на место внутри категории, на грейд не влияет, без достижений — без штрафа. |
| ФСП ID | `integrations/fsp_id.py`, `routers/fsp_id.py`, `routers/mock_fsp_id.py` | Вход и привязка через Keycloak по OIDC (code + PKCE S256). Клиент — по discovery настраиваемого issuer: подпись id_token RS256 по JWKS (неизвестный kid — перечитать ключи), iss, aud, azp, exp/iat, nonce; userinfo с тем же sub. state одноразовый, привязан к браузеру кукой `fsp_flow`; PKCE-верификатор и nonce выводятся HMAC от state и в БД не хранятся; наш токен в URL не попадает (одноразовый билет на минуту). Аккаунт ищется по ФСП ID, затем по подтверждённой почте (автосвязь — только с аккаунтом без профиля и компании); роль меняется по тем же правилам, что во входе по коду. Подтверждённые участия и места из claim `fsp_achievements` идут через импорт протоколов (`source='fsp'`) при согласии на внешние данные. Привязка и отвязка — в настройках кандидата. Мок `/mock-fsp-id` — тот же протокол без Keycloak. |
| Лотерея | `services/lottery.py`, `routers/lottery.py` | Квалифицированная лотерея (Frey & Osterloh): работодатель задаёт порог, пул прошедших замораживается и публикуется `sha256(seed)`, затем жребий. Любой может проверить результат по `pool_ids` и раскрытому `seed`. В пул не попадают те, кто за последние 90 дней отказал этой компании. |
| Синтетика | `seed/generate.py`, `seed/gold.py` | Сначала структура, потом текст: истинный θ, навыки, завышенные резюме (10 %), достижения у ~30 %, CF у ~9 % (только у разработчиков), ~9 % без пройденного теста. Сложные контрпримеры: соседняя специализация, вилка ниже ожиданий. Эталонная релевантность 0–3 считается правилами по скрытым полям, без LLM. |
| Валидация | `services/validation.py`, экран `/v` | Precision@10 и nDCG@10 трёх версий подбора, симуляция рынка, LLM-читер, стабильность, разделяющая сила теста (матрица «истинный грейд × грейд теста», AUC между соседними грейдами, дискриминативность заданий). |
| Резюме и PDF-профиль | `services/parsing.py`, `services/profile_pdf.py`, `GET /api/candidate/profile.pdf` | Резюме, загруженное до создания профиля, сервер не хранит (нет согласия на обработку): `POST /api/candidate/cv` возвращает текст, клиент передаёт его в `POST /api/candidate/profile` (`cv_text`, `cv_filename`) вместе с согласием — так места работы попадают в PDF-профиль без повторной загрузки. Из PDF-резюме — навыки, стаж и категория (для подбора), а также контакты, роли, софт-скиллы и места работы. Контакты только предзаполняют форму самого кандидата; роли и софт-скиллы — справочные (по справочникам `catalog.ROLES` и `SOFT_SKILLS`), видны в карточке, но не влияют на ранжирование и грейд. PDF-профиль — документ кандидата для себя: категория, компетенции θ ± SE, навыки, опыт, достижения, ожидания; места работы в нём — распознанные из резюме, кандидат видит их в профиле с пометкой и может исключить. ## Песочница (задачи на код)

**Как устроено.** В тесте одна задача на код — после четырёх рабочих заданий (`irt.CODE_AT`), если песочница настроена и отвечает на `/health` (проверка раз в 30 с). Пилотная задача на код может прийти раньше, на месте пилотного задания; тогда рабочей задачи на код в этой сессии нет. Семейства (`services/code_items.py`), a и b — экспертная оценка до калибровки, как у остальных семейств:

| Семейство | Что проверяет | Чем отличаются клоны | a | b |
|---|---|---|---|---|
| `code_hash_count` | подсчёт частот словарём | самое частое (при равенстве — меньшее) / первый уникальный / сколько значений встречается ≥ k раз | 1,5 | −1,4 |
| `code_prefix_sums` | префиксные суммы | отрезок [l, r] с 0 / полуинтервал [l, r) / [l, r] с 1 | 1,6 | −1,0 |
| `code_brackets` | стек | правильность / глубина вложенности; набор скобок; пропуск прочих символов | 1,6 | −0,6 |
| `code_binary_search` | бинарный поиск по запросам | < x / ≤ x / первый ≥ x / в отрезке [lo, hi] | 1,7 | 0,0 |
| `code_two_pointers` | два указателя | пары с суммой ≤ t / < t / ≥ t | 1,7 | 0,6 |
| `code_rotated_search` (пилотное) | поиск в циклически сдвинутом массиве | индекс или −1 / есть ли | 1,5 | 1,2 |

У клона своё имя функции, своя деталь условия и свои данные; кандидат видит условие, сигнатуры на Python и TypeScript и 1–2 открытых примера. Скрытые тесты (10–15: примеры, крайние случаи, случайные и большой на 10⁵ — O(n·q) не укладывается в лимит) пересоздаются из сида клона при проверке, ожидаемые ответы считает эталон на Python. Эталоны на обоих языках проходят все скрытые тесты в настоящей песочнице (`sandbox/tests/test_references.py`), шаблон из условия — нет. В базе — только условие, примеры и сид; наружу не уходят ни сид, ни скрытые тесты, ни эталон.

- Ответ: `POST /api/quest/answer {item_id, lang: "python" | "typescript", code, ms, pasted}` → то же состояние сессии, что у других заданий, без вердикта: правильность, как и везде, не показываем до конца теста. Засчитано, если пройдены все скрытые тесты (бинарный исход 2PL). В сессию пишутся язык, код и сводка по тестам — статусы и время, без входных данных.
- «Запустить на примерах»: `POST /api/quest/run {item_id, lang, code}` → `{status, passed, total, results: [{status, time_ms, got, expected}], stderr, runs_left}` — только открытые примеры, до 20 удачных запусков на задачу и не чаще раза в 3 с, на оценку не влияет. Статусы: ok, wrong, tle, mle, re, ce.
- Песочница перегружена (очередь полна или заняты 8 слотов API, `SANDBOX_API_SLOTS`) — 503 «отправьте ещё раз»: задание остаётся текущим, время ответа считается по первой отправке. Песочница ответила не вердиктом (500, битый ответ) — 503 «отправьте ещё раз», задание остаётся текущим, часы идут. До песочницы не достучаться или она сама сообщила о неисправности стенда (503) — 503, задание помечается `void`: не засчитывается ни в плюс, ни в минус, сессия продолжается со следующего задания. Если песочница отклонила само решение (4xx: размер, недопустимые символы), это неверный ответ, а не `void`: нарочно неприемлемым кодом задачу не пропустить.
- Флаги: `code_pasted` — верное решение больше чем наполовину вставлено из буфера (счётчик вставок на клиенте; обходится, поэтому только сигнал для разбора), `too_fast` — как у остальных заданий (лимит на задачу 15 минут). Оба дают `review_required` и не влияют на грейд.
- TypeScript исполняется Node 22 с `--experimental-strip-types`: типы стираются без проверки, `enum` и `namespace` не поддерживаются (сказано в задании; ошибка — «ошибка компиляции» с текстом Node).

**Модель безопасности** (`sandbox/`, Python stdlib + nsjail 3.4):

- Отдельный контейнер `sandbox` во внутренней сети compose (`internal: true`): портов на хост нет, выхода наружу нет, с ним говорит только `api` по общему секрету `SANDBOX_TOKEN` (заголовок `X-Sandbox-Token`, сравнение за постоянное время). Код кандидата и тесты не покидают нашу инфраструктуру — поэтому не e2b и не другие внешние песочницы (152-ФЗ).
- Каждый тест — отдельный запуск nsjail: свои пространства имён (пустая сеть, pid, mount, user, uts, ipc, cgroup), uid/gid 65534 без capabilities и с `no_new_privs`, очищенное окружение. Корень собран из нужного на чтение (`/usr`, `/lib`, `/bin`, `/dev/null`, `/dev/urandom`, `/dev/zero`), решение — `/task` на чтение, запись — только в tmpfs `/tmp` на 8 МБ. Корень самого контейнера — тоже только на чтение.
- Лимиты на тест: 3 с по стенке (меряется снаружи, превышение — tle), RLIMIT_CPU, 256 МБ в cgroup v2 без свопа (куча V8 — 192 МБ), 32 процесса и потока, 1 CPU, файлы и stdout до 8 МБ, 64 дескриптора. На запрос: код до 20 КБ, до 50 тестов, тело до 8 МБ, все тесты — до 60 с. Одновременно 4 прогона (`SANDBOX_WORKERS`), в очереди до 32 запросов, место ждём до 20 с, дальше 503.
- seccomp (`sandbox/policy.kafel`): процесс убивается на ptrace, mount и новом API монтирования, unshare/setns, bpf, perf_event_open, userfaultfd, keyctl, модулях ядра, kexec, clone с флагами новых пространств имён; personality, mknodat, process_madvise, memfd_secret; `socket` и `sched_setaffinity` — EPERM; `clone3`, io_uring и pidfd — ENOSYS (glibc и libuv откатываются на обычные вызовы). Политика — запретительный список поверх сброса capabilities, а не белый список (см. table.md). Журнал nsjail пишется в отдельный файл вне песочницы: подделать «сбой песочницы» через stderr решения нельзя. `/health` повторяет пробный прогон обоих языков раз в 30 с.
- Ожидаемые ответы внутрь nsjail не попадают: решение получает только аргументы, сравнение — снаружи. Фрагмент ошибки (до 400 символов) кандидат видит только для открытых примеров; при отправке API его не отдаёт и не хранит.
- Проверено тестами против настоящего nsjail (CI job `sandbox`): сеть наружу и к соседним сервисам, fork-бомба, бесконечный цикл, 2 ГБ памяти, запись вне `/tmp`, чтение `/etc/passwd` и файлов сервиса, секрет из окружения и `/proc/1/environ`, `os.system` и `child_process`, ptrace/unshare/mount через ctypes, поток вывода, подделка строки результата.
- **Ограничения.** nsjail работает в privileged-контейнере: без этого в Docker нет пространств имён и записи в cgroup. Ядро общее с хостом — уязвимость ядра даёт выход и из песочницы, и из контейнера на хост; seccomp и непривилегированный uid сужают поверхность, но виртуализацию не заменяют. При боевой нагрузке песочницу стоит вынести на отдельную ВМ (или gVisor/Firecracker), тогда privileged ограничен этой ВМ. Время меряется по стенке: на перегруженном хосте возможен ложный tle, поэтому лимит в 6–10 раз выше времени эталона, а прогоны ограничены числом CPU.
- **Ресурсы.** Контейнер `sandbox` — 4 CPU, 3 ГБ, 512 процессов (`cpus`, `mem_limit`, `pids_limit` в compose; на машине меньше чем с 4 CPU задайте `SANDBOX_CPUS` не больше их числа и `SANDBOX_WORKERS` под него — иначе Docker не создаст контейнер). На стенде 8 CPU / 32 ГБ API и Postgres остаётся 4 CPU. Проверка одного решения: Python — до ~1 с, TypeScript — ~2 с (старт Node ≈ 120 мс на тест), эталон на большом тесте — до 0,5 с.

Compose поднимает `sandbox` вместе с API (healthcheck — тот же `/health`); без `SANDBOX_TOKEN` контейнер `sandbox` завершается с сообщением (после трёх перезапусков остаётся остановленным — так и задумано), а API не выдаёт задач на код. Тесты песочницы: `docker build --target test -t fsp-sandbox-test sandbox && docker run --rm --privileged -v "$PWD/backend/app/services/code_items.py:/srv/code_items.py:ro" fsp-sandbox-test`. E2E с песочницей: `docker build --target runtime -t fsp-sandbox sandbox && docker run -d --rm --name sbx --privileged -p 127.0.0.1:8091:8080 -e SANDBOX_TOKEN=dev fsp-sandbox`, затем `SANDBOX_URL=http://127.0.0.1:8091 SANDBOX_TOKEN=dev npm test`. Без `SANDBOX_URL` сценарий `09-code` локально пропускается. В CI песочница настоящая (job `frontend-e2e`), фейковой нет.
