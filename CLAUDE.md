# fsp-lct — ФСП Карьера

Платформа обратного найма ИТ-специалистов для спецтрека ФСП. Кандидат один раз проходит тест и попадает в категорию «специализация · трек · грейд», работодатель сам находит его и шлёт приглашение с вилкой. ТЗ и решения по механикам — в `README.md`; что сделано и что осталось — в `table.md`.

## Структура

- `frontend/` — один `index.html` (брендбук ФСП, без сборки), ходит в API через `fetch`. Раздаётся тем же сервером, что и API.
- `backend/` — FastAPI + PostgreSQL (SQLAlchemy 2.0, sync, psycopg), Python ≥ 3.12, зависимости через `uv`.
  - `app/routers/` — HTTP API по ролям и фичам; `app/services/` — логика (подбор, IRT, лотерея, валидация, LLM); `app/integrations/` — Codeforces, CTFtime, протоколы хакатонов/ФСП; `app/catalog.py` — справочники и правила рынка; `app/models.py` — схема; `migrations/` — ревизии Alembic (накатываются при старте, `app.db.migrate`).
  - `seed/` — генератор синтетики и эталонная релевантность (`gold.py`).
  - `tests/` — pytest, у каждого набора своя база.
- `docker-compose.yml` — `db` + `api`, всё поднимается `docker compose up -d --build`.

## Правила

- **`table.md` ведётся вместе с работой.** Взял задачу — 🔄; закрыл — ✅ в том же коммите; решили отложить — ➖ с причиной; нашли новую дыру — добавь строкой. Таблица — единственный источник правды о том, что осталось.
- **Инварианты домена не ломаются ни в одном изменении** (каждый закреплён тестом):
  - персональные данные кандидата (ФИО, почта, Telegram, `truth`) не участвуют в ранжировании и не уходят работодателю до принятия приглашения или собственного отклика кандидата;
  - вилка «от–до» обязательна в приглашении и вакансии, правила — `validate_fork` и `catalog.py`;
  - контакты раскрываются только после согласия кандидата, каждое раскрытие пишется в `AuditLog`;
  - грейд не понижается принудительно, повышение — по θ − SE и не чаще `UPGRADE_COOLDOWN_DAYS`;
  - достижения (ФСП, CF, хакатоны) влияют на место внутри категории, но не на грейд; нет достижений — нет штрафа.
- **152-ФЗ.** Согласия раздельные (обработка, публикация профиля, внешние данные), каждое изменение пишется в `ConsentEvent` с версией текста. Согласие действует, только если версия совпадает с текущей `CONSENT_VERSION` (`matching.consent_ok`): сменили текст — кандидат скрыт до повторного согласия. Без согласия на публикацию кандидат не виден работодателям. У кандидата есть выгрузка своих данных и удаление аккаунта. В логи и `AuditLog.detail` ПДн не пишутся — только идентификаторы.
- **Секреты не хранятся открытым текстом.** Токены сессий — sha256 (`deps.hash_secret`), коды входа — HMAC с серверным перцем `SECRET_KEY` (`deps.otp_hash`): шестизначный код по голому sha256 перебирается за секунды. Код Codeforces — sha256 со сроком действия. В фикстурах тестов токен выдаётся через `deps.issue_token`. Пароли и ключи — только из окружения.
- **Демо-режим только явно.** `DEMO=1` открывает вход за демо-персонажей, код почты в ответе и ФСП ID без OAuth. По умолчанию выключен; включается в compose для стенда жюри.
- **LLM необязательна.** Любой вызов `services/llm.py` возвращает `None` при недоступности модели, у вызывающего кода обязателен фолбэк на правила. Модели — локальные, через OpenAI-совместимый API.
- **Схема меняется только вместе с ревизией Alembic.** Поменял `models.py` — `cd backend && uv run alembic revision --autogenerate --rev-id NNNN_slug -m "что меняется"` (id — `NNNN_slug`, не длиннее 32 символов), ревизию вычитываешь руками (частичные индексы с `postgresql_where`, `server_default`, `ondelete`, переименования autogenerate видит как drop + add — перепиши на `alter_column`, данные переноси в самой ревизии). Корень — `0001_baseline` (схема на момент перехода с `create_all`). Параллельные ветки добавляют ревизию поверх своей базы (`down_revision` — голова `main` на момент ответвления); при старте применяется `alembic upgrade heads` — все головы. Если после мёржа на `main` две головы — отдельным коммитом `uv run alembic merge heads --rev-id NNNN_merge_… -m "merge"`. `tests/test_migrations.py` ловит модель без ревизии: после `upgrade heads` autogenerate-сверка пуста, а определения индексов и ограничений (предикаты частичных индексов, `ondelete`) совпадают с `create_all`. Наборы тестов для скорости создают схему `create_all`, приложение и `seed.generate` — только миграциями.
- **Подбор и тест меняются вместе с валидацией.** Тронул `matching.py`, `irt.py`, `items.py`, `catalog.py` или `seed/` — перепрогони `uv run python -m app.services.validation` и обнови цифры в `README.md`. Коэффициенты не подгоняются перебором по эталону: эталон считается правилами по скрытым полям синтетики, и подгонка под него — замкнутый круг.
- **Данные только синтетические.** Реальные ПДн в репозиторий, сид и тесты не попадают. Внешние API (Codeforces, CTFtime) в тестах замоканы, живые проверки — только с `LIVE=1`.
- **Код минимальный.** Без абстракций «на будущее». Осознанное упрощение помечается `# ponytail: <потолок>, <как расширять>`. Комментарии и сообщения об ошибках — по-русски, идентификаторы — по-английски.

## Тесты

- Бэкенд: `./backend/test.sh` — пересоздаёт с нуля тестовые базы (`fsp_flows`, `fsp_quest`, `fsp_integ`, `fsp_seed`, `fsp_valid`, `fsp_validtest`, `fsp_vac`, `fsp_auth`, `fsp_priv`, `fsp_gen`, `fsp_migr`, `fsp_chat`) и гоняет каждый набор в своей базе с `DEMO=1`, копит покрытие по всем наборам (`pytest-cov`, `--cov-append`) и в конце печатает `coverage report -m`; ниже 80 % — скрипт падает (порог — `COV_MIN`). Новый набор — строкой `база:файл` в `SUITES` и базой в списке создания. Демо-база `fsp` в тестах не используется. Нужен Postgres: `docker compose up -d db` (другой сервер — `PG=postgresql+psycopg://fsp:fsp@localhost:5434 ./backend/test.sh`).
- Один набор с покрытием: `cd backend && DEMO=1 DATABASE_URL=postgresql+psycopg://fsp:fsp@localhost:5432/fsp_auth uv run pytest -q --cov --cov-report=term-missing tests/test_auth.py`. Наборы с засевом синтетики помечены `slow` (`-m 'not slow'` — пропустить).
- Фронт (e2e): `cd frontend && npm ci && npx playwright install chromium && npm test`. Playwright сам поднимает бэкенд (`frontend/e2e/server.sh`): своя база `fsp_e2e` (создаётся, если нет; демо-база `fsp` не трогается), пересев `seed.generate --reset --candidates 200 --needs 20` на каждый прогон, `DEMO=1`, без LLM, порт 8010 (`E2E_PORT`). Сценарии идут последовательно в одном воркере (`01-…05-*.spec.js`, `08-chat.spec.js`), сценарии с общим состоянием (приглашение → принятие → контакты) — внутри одного теста. В каждом тесте снимается V8-покрытие inline-скрипта `index.html` (monocart); порог 80 % строк — `COV_MIN`, ниже — `npm test` падает; отчёт `frontend/coverage/index.html`, номера непокрытых строк — `frontend/coverage/uncovered-lines.txt`. `page.route` — только где живой бэкенд непрактичен: внешние Codeforces/CTFtime, дашборд `/v` (результат прогона лежит в общем `backend/var/validation.json`), инъекция ошибок 5xx/сети. Новый экран или действие во фронте — сценарий в `frontend/e2e/`, проверки по видимому тексту и ответам API.
- Новая фича или исправление приходят с тестом в наборе своего модуля. Самопроверки в модулях (`uv run python -m app.services.irt`, `…lottery`, `…parsing`, `app.integrations.scoring`) тоже должны быть зелёными.
- Покрытие бэкенда и фронта — не ниже 80 %. Опускать его нельзя; новый код без тестов не принимается.
- В CI бэкенд гоняется на Python 3.12 (как в Dockerfile) — код должен работать на 3.12, даже если локальный venv новее.

## Git-процесс

- Ветка от `main`, коммиты, затем PR (`gh pr create --base main`). Пуш в `main` напрямую запрещён.
- **CI — `.github/workflows/ci.yml`**, запускается на каждый PR и на пуш в `main`: бэкенд-тесты (`./backend/test.sh` против Postgres из service-контейнера), самопроверки модулей, синтаксис JS и e2e фронта (job `frontend-e2e`: Playwright + покрытие ≥ 80 %, отчёты — артефакты `frontend-coverage` и `playwright-report`). PR мёржится только с зелёным CI. Новый набор тестов или самопроверка добавляются в `ci.yml` в том же коммите. Перед пушем те же шаги гоняются локально — CI подтверждает, а не ищет ошибки за тебя.
- **Перед открытием PR изменения обязательно верифицирует сторонний агент** — Codex (`codex`) или antigravity cli (`agy`). Даёшь ему итоговый diff (`git diff main...HEAD`) и задачу: найти ошибки, нарушения инвариантов и правил из этого файла, незакрытые хвосты (`table.md`, README, тесты, `ci.yml`). Codex запускается только на чтение: `codex exec -s read-only -C <repo> -o <файл-отчёта> "<задача>" < /dev/null` (без закрытого stdin в фоне Codex зависает на «Reading additional input from stdin»).
  - Замечания правятся до открытия PR, а не после; после правок верификация повторяется на итоговом diff. Стоп-условие: нет замечаний уровня critical и high. Каждое medium/low либо исправлено, либо записано в `table.md` (➖ с причиной или ⬜ с планом) — молча не пропускается. Продакшен-доводку за рамками MVP (cookie-сессии, rate limit на прокси, миграции и т. п.) ревьюер может требовать бесконечно: её фиксируем в `table.md`, а не блокируем PR.
  - Если ни `codex`, ни `agy` недоступны (не установлены, нет авторизации, падают), ревью проводит субагент Claude Code (Agent) с той же задачей. Без верификации PR не открывается.
  - В описании PR — каким агентом прошла верификация (`codex` / `agy` / субагент), сколько раундов и что найдено (или что замечаний нет).
- Заголовок коммита — Conventional Commits: `<type>(<scope>): <что сделано>`, `type` — `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `build`; `scope` — `backend`, `frontend`, `seed`, `validation` или `repo` (CLAUDE.md, compose, table.md). Повелительное наклонение, до ~72 символов, без точки.
- Тело коммита и описание PR — четыре блока: саммари; затронутые части (`backend`, `frontend`, …); затронутые файлы; решаемая проблема или фича.

  ```
  feat(backend): добавь поиск по банку кандидатов

  Саммари: эндпоинт GET /api/employer/search — анонимные карточки с
  фильтрами по специализации, грейду, стеку и достижениям ФСП.

  Части: backend

  Файлы:
  - backend/app/routers/employer.py
  - backend/tests/test_flows.py
  - table.md

  Проблема: ТЗ требует поиск по всей базе, а была только подборка под потребность.
  ```
