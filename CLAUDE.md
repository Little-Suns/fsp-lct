# fsp-lct — ФСП Карьера

Платформа обратного найма ИТ-специалистов для спецтрека ФСП. Кандидат один раз проходит тест и попадает в категорию «специализация · трек · грейд», работодатель сам находит его и шлёт приглашение с вилкой. ТЗ и решения по механикам — в `README.md`; что сделано и что осталось — в `table.md`.

## Структура

- `frontend/` — один `index.html` (брендбук ФСП, без сборки), ходит в API через `fetch`. Раздаётся тем же сервером, что и API.
- `backend/` — FastAPI + PostgreSQL (SQLAlchemy 2.0, sync, psycopg), Python ≥ 3.12, зависимости через `uv`.
  - `app/routers/` — HTTP API по ролям и фичам; `app/services/` — логика (подбор, IRT, банк заданий `items.py` + сценарные банки специализаций `bank/`, задачи на код `code_items.py`, лотерея, валидация, LLM, разбор резюме, PDF-профиль, автопроверка заданий работодателя); `app/integrations/` — Codeforces, CTFtime, протоколы хакатонов/ФСП, клиент ФСП ID (OIDC); `app/catalog.py` — справочники и правила рынка; `app/models.py` — схема; `migrations/` — ревизии Alembic (накатываются при старте, `app.db.migrate`).
  - `seed/` — генератор синтетики и эталонная релевантность (`gold.py`).
  - `tests/` — pytest, у каждого набора своя база.
- `sandbox/` — песочница задач на код: HTTP-сервис на stdlib Python, каждый тест — отдельный nsjail (Python 3.11, TypeScript на Node 22); банк задач — `backend/app/services/code_items.py`, клиент — `services/sandbox.py`. Модель безопасности и ограничения — README «Песочница».
- `docker-compose.yml` — `db` + `api` + `sandbox` (privileged, только внутренняя сеть), всё поднимается `docker compose up -d --build`; без `SANDBOX_TOKEN` тест идёт без задач на код. При `DEMO=1` `api` перед стартом засевает пустую базу (`seed.generate --if-empty --today now`), засеянную не трогает.
- **API — строго один процесс uvicorn** (`WEB_CONCURRENCY=1` в `backend/Dockerfile` и compose): SSE чата (`chat.Hub`), троттлинг Codeforces/CTFtime, случайный по умолчанию `SECRET_KEY`, одна проверка кода на сессию (`quest._one_check`), кэш `/health` песочницы и мок ФСП ID живут в памяти процесса — второй воркер их ломает. Запас одного процесса — нагрузочный прогон `backend/loadtest/` (README, `table.md`).

## Правила

- **`table.md` ведётся вместе с работой.** Взял задачу — 🔄; закрыл — ✅ в том же коммите; решили отложить — ➖ с причиной; нашли новую дыру — добавь строкой. Таблица — единственный источник правды о том, что осталось.
- **Инварианты домена не ломаются ни в одном изменении** (каждый закреплён тестом):
  - персональные данные кандидата (ФИО, почта, Telegram, `truth`) не участвуют в ранжировании и не уходят работодателю до принятия приглашения или собственного отклика кандидата;
  - вилка «от–до» обязательна в приглашении и вакансии, правила — `validate_fork` и `catalog.py`;
  - контакты раскрываются только после согласия кандидата, каждое раскрытие пишется в `AuditLog`;
  - грейд не понижается принудительно, повышение — по θ − SE и не чаще `UPGRADE_COOLDOWN_DAYS`;
  - достижения (ФСП, CF, хакатоны) влияют на место внутри категории, но не на грейд; нет достижений — нет штрафа;
  - отзыв кандидата о компании — только по принятому приглашению и не раньше `COMPANY_FEEDBACK_AFTER_DAYS` (в `DEMO=1` — сразу, `reputation.feedback_after_days`); кандидату репутация компании не показывается, отзывы меняют только квоту и блок (`services/reputation.py`); работодатель видит сводку без авторов.
- **152-ФЗ.** Согласия раздельные (обработка, публикация профиля, внешние данные), каждое изменение пишется в `ConsentEvent` с версией текста. Согласие действует, только если версия совпадает с текущей `CONSENT_VERSION` (`matching.consent_ok`): сменили текст — кандидат скрыт до повторного согласия. Без согласия на публикацию кандидат не виден работодателям. У кандидата есть выгрузка своих данных и удаление аккаунта. В логи и `AuditLog.detail` ПДн не пишутся — только идентификаторы.
- **Секреты не хранятся открытым текстом.** Токены сессий — sha256 (`deps.hash_secret`), коды входа — HMAC с серверным перцем `SECRET_KEY` (`deps.otp_hash`): шестизначный код по голому sha256 перебирается за секунды. Код Codeforces — sha256 со сроком действия. В фикстурах тестов токен выдаётся через `deps.issue_token`. Пароли и ключи — только из окружения.
- **Демо-режим только явно.** `DEMO=1` открывает вход за демо-персонажей (общий демо-токен — HMAC адреса на `SECRET_KEY`; при `DEMO=0` не действует), код почты в ответе, пересчёт валидации кнопкой на `/v` без входа и мок-провайдер ФСП ID (`/mock-fsp-id`, OIDC как у Keycloak; отдельно — `FSP_ID_MOCK=1`) и отзыв о компании сразу после принятия приглашения (без недели ожидания). Клиент ФСП ID — настоящий OIDC (code + PKCE, проверка id_token по JWKS): боевой Keycloak подключается только конфигурацией `FSP_ID_*`. По умолчанию выключен; включается в compose для стенда жюри.
- **LLM необязательна.** Провайдер — `LLM_PROVIDER`: `none` (по умолчанию и в compose — только правила), `ollama` (локальная `mistral:7b` + `bge-m3`), `openai_compatible` (свой шлюз), `yandexgpt`, `gigachat`; все — через OpenAI-совместимый клиент `services/llm.py`. Любой вызов возвращает `None` при выключенной или недоступной модели, у вызывающего кода обязателен фолбэк на правила. ПДн в модель не уходят: свободный текст (резюме, потребность) перед любым вызовом проходит `parsing.mask_pii`, подбор шлёт только структурные поля без ФИО. Живой смоук — только вручную (`LIVE_LLM=1 tests/test_llm_live.py`).
- **Схема меняется только вместе с ревизией Alembic.** Поменял `models.py` — `cd backend && uv run alembic revision --autogenerate --rev-id NNNN_slug -m "что меняется"` (id — `NNNN_slug`, не длиннее 32 символов), ревизию вычитываешь руками (частичные индексы с `postgresql_where`, `server_default`, `ondelete`, переименования autogenerate видит как drop + add — перепиши на `alter_column`, данные переноси в самой ревизии). Корень — `0001_baseline` (схема на момент перехода с `create_all`). Параллельные ветки добавляют ревизию поверх своей базы (`down_revision` — голова `main` на момент ответвления); при старте применяется `alembic upgrade heads` — все головы. Если после мёржа на `main` две головы — отдельным коммитом `uv run alembic merge heads --rev-id NNNN_merge_… -m "merge"`. `tests/test_migrations.py` ловит модель без ревизии: после `upgrade heads` autogenerate-сверка пуста, а определения индексов и ограничений (предикаты частичных индексов, `ondelete`) совпадают с `create_all`. Наборы тестов для скорости создают схему `create_all`, приложение и `seed.generate` — только миграциями.
- **Экспресс-тест — только предварительная категория.** `mode=express`: `irt.EXPRESS_ITEMS` заданий по `EXPRESS_TIME_LIMIT_S`, только `irt.EXPRESS_KINDS` (без ревью и задач на код), без пилотного; грейд ставится лишь тому, у кого его нет (`Candidate.grade_express`), кулдаун не запускает и существующий грейд не меняет. Полный тест после экспресса — первое присвоение.
- **Подбор и тест меняются вместе с валидацией.** Тронул `matching.py`, `irt.py`, `items.py`, `catalog.py` или `seed/` — перезасей отдельную базу и перепрогони валидацию (`DATABASE_URL=…/fsp_valid uv run python -m seed.generate --reset`, затем `DATABASE_URL=…/fsp_valid uv run python -m app.services.validation`) и обнови цифры в `README.md` — все из одного прогона. Синтетика детерминирована по `--seed` и `--today` (по умолчанию фиксированная дата `DEMO_TODAY` = 2026-10-05, от неё все сроки; `--today now` — реальная дата, так засевают стенд и e2e), поэтому цифры не плавают от дня ко дню. Коэффициенты не подгоняются перебором по эталону: эталон считается правилами по скрытым полям синтетики, и подгонка под него — замкнутый круг.
- **Данные только синтетические.** Реальные ПДн в репозиторий, сид и тесты не попадают. Внешние API (Codeforces, CTFtime) в тестах замоканы, живые проверки — только с `LIVE=1`.
- **Код минимальный.** Без абстракций «на будущее». Осознанное упрощение помечается `# ponytail: <потолок>, <как расширять>`. Комментарии и сообщения об ошибках — по-русски, идентификаторы — по-английски.

## Тесты

- Бэкенд: `./backend/test.sh` — пересоздаёт с нуля тестовые базы (`fsp_flows`, `fsp_quest`, `fsp_integ`, `fsp_seed`, `fsp_valid`, `fsp_validtest`, `fsp_validday`, `fsp_vac`, `fsp_auth`, `fsp_priv`, `fsp_gen`, `fsp_migr`, `fsp_chat`, `fsp_fspid`, `fsp_code`, `fsp_rep`) и гоняет каждый набор в своей базе с `DEMO=1`, копит покрытие по всем наборам (`pytest-cov`, `--cov-append`) и в конце печатает `coverage report -m`; ниже 80 % — скрипт падает (порог — `COV_MIN`). Новый набор — строкой `база:файл` в `SUITES` и базой в списке создания. Демо-база `fsp` в тестах не используется. Нужен Postgres: `docker compose up -d db` (другой сервер — `PG=postgresql+psycopg://fsp:fsp@localhost:5434 ./backend/test.sh`).
- Один набор с покрытием: `cd backend && DEMO=1 DATABASE_URL=postgresql+psycopg://fsp:fsp@localhost:5432/fsp_auth uv run pytest -q --cov --cov-report=term-missing tests/test_auth.py`. Наборы с засевом синтетики помечены `slow` (`-m 'not slow'` — пропустить).
- Фронт (e2e): `cd frontend && npm ci && npx playwright install chromium && npm test`. Playwright сам поднимает бэкенд (`frontend/e2e/server.sh`): своя база `fsp_e2e` (создаётся, если нет; демо-база `fsp` не трогается), пересев `seed.generate --reset --candidates 200 --needs 20 --today now` на каждый прогон, `DEMO=1`, без LLM, порт 8010 (`E2E_PORT`). Сценарии идут последовательно в одном воркере (`01-…06-*.spec.js`, `08-chat.spec.js`, `09-*.spec.js` — ФСП ID, задача на код, телефон и планшет, `10-theme.spec.js` — тёмная тема и переключатель, `11-rerender.spec.js` — перерисовка без анимации, фокус и прокрутка), сценарии с общим состоянием (приглашение → принятие → контакты) — внутри одного теста. В каждом тесте снимается V8-покрытие inline-скрипта `index.html` (monocart); порог 80 % строк — `COV_MIN`, ниже — `npm test` падает; отчёт `frontend/coverage/index.html`, номера непокрытых строк — `frontend/coverage/uncovered-lines.txt`. `page.route` — только где живой бэкенд непрактичен: внешние Codeforces/CTFtime, дашборд `/v` (результат прогона лежит в общем `backend/var/validation.json`), инъекция ошибок 5xx/сети. В CI e2e автоматически не идёт (только вручную, `workflow_dispatch`), поэтому перед PR его гоняют локально. Новый экран или действие во фронте — сценарий в `frontend/e2e/`, проверки по видимому тексту и ответам API.
- Песочница: в бэкенд-тестах клиент песочницы замокан (`tests/test_code.py`); сама песочница проверяется против настоящего nsjail в Docker — `docker build --target test -t fsp-sandbox-test sandbox && docker run --rm --privileged -v "$PWD/backend/app/services/code_items.py:/srv/code_items.py:ro" fsp-sandbox-test` (CI job `sandbox`: вердикты, попытки выхода, эталоны банка на обоих языках). Поменял `sandbox/` или `code_items.py` — гоняешь их. E2E задачи на код (`09-code.spec.js`) идёт с настоящей песочницей: `SANDBOX_URL`/`SANDBOX_TOKEN` в окружении `npm test` (как поднять — README «Песочница»); без них локально пропускается, при ручном запуске CI — обязателен.
- Новая фича или исправление приходят с тестом в наборе своего модуля. Самопроверки в модулях (`uv run python -m app.services.irt`, `…lottery`, `…parsing`, `app.integrations.scoring`) тоже должны быть зелёными.
- Покрытие бэкенда и фронта — не ниже 80 %. Опускать его нельзя; новый код без тестов не принимается.
- В CI бэкенд гоняется на Python 3.12 (как в Dockerfile) — код должен работать на 3.12, даже если локальный venv новее.

## Git-процесс

- Ветка от `main`, коммиты, затем PR (`gh pr create --base main`). Пуш в `main` напрямую запрещён.
- **CI — `.github/workflows/ci.yml`**, запускается на каждый PR и на пуш в `main` (e2e — только вручную): бэкенд-тесты (`./backend/test.sh` против Postgres из service-контейнера), самопроверки модулей, песочница против настоящего nsjail (job `sandbox`), синтаксис JS фронта (job `frontend-syntax`). E2E фронта (job `frontend-e2e`: Playwright с настоящей песочницей + покрытие ≥ 80 %, отчёты — артефакты `frontend-coverage` и `playwright-report`) в CI запускается вручную (`workflow_dispatch`: Actions → CI → Run workflow), а перед PR его гоняют локально (`npm test`). PR мёржится только с зелёным CI. Новый набор тестов или самопроверка добавляются в `ci.yml` в том же коммите. Перед пушем те же шаги гоняются локально — CI подтверждает, а не ищет ошибки за тебя.
- **Перед открытием PR изменения обязательно верифицирует сторонний агент** — Codex (`codex`) или antigravity cli (`agy`). Даёшь ему итоговый diff (`git diff main...HEAD`) и задачу: найти ошибки, нарушения инвариантов и правил из этого файла, незакрытые хвосты (`table.md`, README, тесты, `ci.yml`). Codex запускается только на чтение: `codex exec -s read-only -C <repo> -o <файл-отчёта> "<задача>" < /dev/null` (без закрытого stdin в фоне Codex зависает на «Reading additional input from stdin»).
  - Замечания правятся до открытия PR, а не после; после правок верификация повторяется на итоговом diff. Стоп-условие: нет замечаний уровня critical и high. Каждое medium/low либо исправлено, либо записано в `table.md` (➖ с причиной или ⬜ с планом) — молча не пропускается. Продакшен-доводку за рамками MVP (cookie-сессии, rate limit на прокси, миграции и т. п.) ревьюер может требовать бесконечно: её фиксируем в `table.md`, а не блокируем PR.
  - Если ни `codex`, ни `agy` недоступны (не установлены, нет авторизации, падают), ревью проводит субагент Claude Code (Agent) с той же задачей. Без верификации PR не открывается.
  - В описании PR — каким агентом прошла верификация (`codex` / `agy` / субагент), сколько раундов и что найдено (или что замечаний нет).
- Заголовок коммита — Conventional Commits: `<type>(<scope>): <что сделано>`, `type` — `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `build`; `scope` — `backend`, `frontend`, `seed`, `validation` или `repo` (CLAUDE.md, compose, table.md). Повелительное наклонение, до ~72 символов, без точки.
- Тело коммита и описание PR — четыре блока: саммари; затронутые части (`backend`, `frontend`, …); затронутые файлы; решаемая проблема или фича.

  ```
  feat(backend): добавь поиск по банку кандидатов

  Саммари: эндпоинт GET /api/employer/search — анонимные карточки с
  фильтрами по специализации, грейду, стеку и достижениям ФСП.

  Части: backend

  Файлы:
  - backend/app/routers/employer.py
  - backend/tests/test_flows.py
  - table.md

  Проблема: ТЗ требует поиск по всей базе, а была только подборка под потребность.
  ```
